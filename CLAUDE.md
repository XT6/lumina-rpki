# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Lumina is an RPKI relying party (validator) written from scratch in **Elixir on the Erlang VM**. `GOAL.md` is the project charter; read it before starting larger work.

## Commands

Toolchain versions are pinned in `.tool-versions` (Erlang/OTP 29.1.2, Elixir 1.20.5).

```sh
scripts/install-deps.sh [--check]  # install (or only check) Erlang/OTP, Elixir, rsync >= 3.1.0, dev deps, ./lumina
mix compile --warnings-as-errors   # build; warnings fail the build
mix test                           # full test suite (includes doctests)
mix test test/lumina_test.exs      # one test file
mix test test/lumina_test.exs:5    # one test, by line number
mix format                         # format code
mix dialyzer                       # type analysis; PLTs are cached in priv/plts/ (git-ignored)
mix check                          # everything CI runs: compile (warnings as errors), format check, tests, catalog and ASN.1 extraction checks, Dialyzer
mix lumina.rfc_coverage [--rfc N]  # which RFC sections the tests and fixtures cover
mix lumina.fixtures.gen [ID...]    # regenerate Barry fixtures (needs scripts/install-barry.sh)
mix test --only barry              # tests that run the real Barry binary (excluded when it isn't installed)
mix test --only rsync              # tests against a real rsync daemon (Lumina.Test.RsyncDaemon); excluded without rsync >= 3.1.0
mix test --only network            # tests against the live RPKI (the M3, M4, M5 and M6 done tests sync LACNIC); never run by default, takes minutes
mix test --only realrepo           # tests against the local, git-ignored LACNIC repository copy in test/realrepos/ (excluded without it)
mix lumina.test_catalog            # regenerate doc/tests/CATALOG.md after adding or changing a test or fixture
mix escript.build && ./lumina print [--brief] FILE...   # print RPKI objects and .tal files (Lumina.CLI, Lumina.Print)
./lumina sync [--cache DIR] [--tal FILE]... [--timeout S] [--max-depth N] [--per-host N] [--rsync PATH] [--progress | --quiet]   # fetch TAs and repositories (Lumina.Sync); without --tal it uses every TAL in ./tals/ and fetches the live RIR repositories
./lumina validate [--cache DIR] [--tal FILE]... [--now TIME] [--max-invalid PERCENT] [--progress | --quiet]   # validate the cache offline from each TAL's stored TA (Lumina.Validate); exit 1 if a TA is missing or invalid, or more than PERCENT (10) of a TAL's certificates are invalid (D-022)
elixir scripts/token_usage.exs     # regenerate doc/token-usage.md (Claude Code token usage per milestone, at API prices) from the session transcript and GitHub; commit it with every PR
./lumina vrps [--cache DIR] [--tal FILE]... [--now TIME] [--max-invalid PERCENT] [--format csv|json] [--output FILE] [--wide] [--progress | --quiet] [--sync [--max-age DURATION] [--timeout S] [--max-depth N] [--per-host N] [--rsync PATH]]   # with --sync, first sync the TALs with no TA in the cache or last synced more than DURATION (1h) ago (D-037, #185; Sync.last_synced/2; the sync makes the exit code 1 only if a TA or its own publication point wasn't fetched, Sync.ta_synced?/1, deeper failures only warn); then validate offline and write the VRPs as CSV in Routinator's columns or as Lumina's JSON (Lumina.VRP, D-031 to D-034, #167; both formats in doc/output.md; --wide adds the ROA's URI and keeps duplicates, #166); summary on stderr; --output replaces the file atomically; exit 1 as validate, but the VRPs are still written
mix lumina.compare_vrps [--csv FILE | --url URL] [--limit N] LUMINA_CSV   # compare lumina vrps output with Routinator's published CSV, downloaded now (Lumina.VRPCompare, D-035, #168): per trust anchor, counts and the VRPs only one side has; names mapped (ripe-ncc → ripe, apnic-rfc7730-https → apnic)
mix lumina.asn1.extract            # regenerate asn1/rfc/ (verbatim from doc/rfc) and asn1/build/ (with asn1/patches/ applied)
```

## Tests

Every test module needs a `@moduledoc` saying what it covers and why. Every test name states the behaviour checked, and `@tag doc: "..."` adds detail. Write literal `test "..."` blocks, not tests generated in loops. The suite fails on an undocumented module. After adding, renaming or re-documenting tests or fixtures, run `mix lumina.test_catalog`, or CI fails.

Tag every test that checks an RFC requirement with the section it comes from, for example `@tag rfc: "6487#4.8.9"`. Use literal strings, not attributes. References are checked against the section headings in `doc/rfc/`, and an invalid one fails the suite. Full convention: `doc/testing.md`.

Repository fixtures live in `test/fixtures/barry/<id>/`: a hand-written `case.repo` (Barry descriptor) and `case.exs` (metadata), plus generated output that is committed. Every fixture must state its rationale, RFC references and expected outcome, or the suite fails. A reject may add `rule:` (the Chain/Profile rule, or for a `.crl` the CRL's rule); the M4 done test (`M4DoneTest`) requires the certificates `lumina validate` finds invalid to be exactly those, at 2030-01-01, and the M5 done test (`M5DoneTest`) the same of publication points (failed exactly when a ruled reject names the manifest or the CRL) and signed objects, and the M6 done test (`M6DoneTest`) that the certificates found overclaiming are exactly the `resources_not_encompassed` rejects, listed and counted by both commands. Fixture objects are valid from 2026-01-01 to 2036-01-01 unless a fixture overrides this, so validate fixtures at a fixed time, never "now". Load fixtures in tests with `Lumina.Test.Fixture.load!("m0-minimal-valid")` (`test/support/`). Test TALs: hand-written cases in `test/fixtures/tals/cases/<id>/` (`case.tal` byte-exact and never normalized, `case.exs` metadata). Their rule vocabulary and line semantics are in `test/fixtures/tals/README.md`, and every rule must keep at least one case. The five RIR TALs are in `test/fixtures/tals/rir/`, byte-exact, with source, date, SHA-256 and terms in its README. Never edit them, and update one only after the maintainer reviews the change. The production TALs in the top-level `tals/` folder (D-004) are byte-exact copies of these; a test fails if the two differ. TALs are parsed by `Lumina.TAL.parse/1` / `decode_file/1` (strict grammar, D-002), giving comments, URIs, the SPKI DER (`public_key`), `subject_key_identifier/1` and `key_bits/1`. `Lumina.TAL.check_ta(tal, cert)` checks a TA certificate against its TAL per RFC 8630 §2.3/§3: exact key, self-issued CA, AKI = SKI, and resources present, non-empty and not inherit; `Lumina.Chain.ta/3` adds the signature, dates and profile. `Lumina.TAL.uris_by_preference/1` gives the fetch order (D-003): HTTPS first, then rsync, TAL order within each; on failure or key mismatch, try the next. Repository URIs: `Lumina.URI.parse/1` (strict; rejects dot segments, percent-encoding, user info, queries; drops the default port and a trailing slash), `module/1` (first path segment, and the unit of fetching: the walk fetches the module of each publication point not already covered, D-012) and `cache_path/2` (`<root>/<scheme>/<host[:port]>/<path>`, always inside the root). Fetching decisions: D-005, D-007, D-008, D-010, D-011, D-012 (D-006 and D-009 superseded). The cache (`Lumina.Cache`): fetches go into `stage/1`, then `commit/3` swaps them in (removing symlinks and special files) or `discard/1` drops them, so a failure keeps the last good copy; `put_file/3` for single files; `recover/1` repairs an interrupted swap; `record/4`/`status/2` keep each URI's last attempt and success. Working dirs under the root start with a dot (`.staging`, `.aside`, `.status`). rsync: `Lumina.Rsync.fetch_dir/3` (a directory, recursive; the walk passes modules, D-012) and `fetch_file/3`, fixed safe flags and D-008 limits (connect timeout 10 s, which covers only the TCP connection; a server that accepts and stays silent hits the 300 s I/O timeout), typed error reasons, oversize files skipped and reported. Sources are always `rsync://host/module/./path` so a path can't become a server-side option (F-025). HTTPS: `Lumina.HTTPS.fetch/2` (single files such as TA certificates, RFC 8630 §4): `:ssl` with peer and host name verification against the system CA store (`:cacerts` overrides it, for tests), TLS 1.2+, validation failures logged, wildcard-only matches accepted but warned (D-010), redirects HTTPS-only and at most 3, D-008 size and timeout limits, typed error reasons. It speaks HTTP/1.1 itself because `:httpc` can't bound every body (F-026). Tests use `Lumina.Test.HTTPSServer` with certificates generated per test. TA retrieval: `Lumina.TA.retrieve(tal, root, opts)` tries the TAL's URIs in D-003 order, decodes and validates each (`Chain.ta/3` at `:now`, D-014), accepts the first that validates and stores it at `<root>/.ta/<ski hex>.cer` (with a `.json` note of URI and time); every attempt is listed, and if all fail the error carries the previously accepted TA as `:stale` if it still validates (`cached/3`). Cache working dirs now include `.ta` and `.valid` (last valid copies, `Lumina.LastValid`, D-023: one per manifest URI, saved by `lumina sync` when a point is accepted; `Validate.point(..., last_valid: root, save: true)` falls back to it when the live point fails and the copy is still accepted, status `:fallback`, walk issue `point_fallback`). Replay protection (`Lumina.ManifestState`, D-024, #136): per CA (by SKI) the last accepted manifest's URI, number and thisUpdate in `<cache>/.state/manifests/`; with `last_valid:` set, a new manifest that doesn't move forward fails the point (`manifest_number_replay`, `manifest_this_update_replay`; a changed file name skips the number check with `manifest_name_changed`, RFC 9981); `save: true` records accepted points. Repository walk: `Lumina.Walk.run(ta_cert, root, opts)` (RFC 6481 §5) fetches the module of each CA's `caRepository` once per run (skipping publication points in a module already fetched, D-012; `Lumina.Sync` passes each walk's `fetched` and `refetched` to the next TAL's walk, so a module shared by several trees is fetched once per sync and a failed one isn't retried, #102), follows only CA certificates (Basic Constraints cA, or keyCertSign) listed on the current manifest of an accepted publication point (`Lumina.PublicationPoint`, #134) that validate against that CA (`Lumina.Validate.point/5`: `Chain.child/6` with the CRL in that publication point; invalid ones are `:invalid` issues, warnings `:warning` issues, a failed point a `:point_failed` issue with nothing below it walked; points carry `status`, D-014) and then `Walk.repository/1` (D-005), fetches a module once more when a point fetched this run fails only with `file_missing`/`hash_mismatch` (caught mid-update, RFC 6481 §5, D-007, #137; issue `refetched`, at most once per module per run; `:before_refetch` is a test hook), stops at `:max_depth` (32) and at loops (a publication point is identified by its CA's manifest URI, `Walk.point_key/2`: CAs sharing a `caRepository` directory, each with its own manifest, are each walked and validated, RFC 9286 §1, #195; `m7-shared-point`, and `m7-shared-manifest` for a duplicate), plans and reports one level at a time in walk order, but fetches and validates without waiting for the level (#88): a point is validated as soon as its module is in, and its valid children's modules are fetched and their points validated ahead (results reused only for the same certificate and resources; a refetch drops those of its module), at most `:per_host` (8) rsync runs at once per host (D-011; `lumina sync --per-host N`), one validation per scheduler, keeps the last good copy on failure, and returns `points`, `fetches` and `issues`. `:remap` (tests only) points fixture hosts such as `localhost:8873` at a test daemon. Walk fixtures are `m3-walk-*`; a fixture's `rsync_modules` (case.exs) adds modules to `localhost:8873`, and `fixture.modules` lists them for a test daemon. A sync run (`Lumina.Sync.run/3`) recovers the cache, holds `<cache>/.lock` (process id; a dead holder's lock is taken over), retrieves each TA and walks from it (from the stale TA if retrieval failed). Offline validation (`Lumina.Validate.run/3`, `lumina validate`, #114) starts from the TA stored in the cache (`TA.stored/2`, not revalidated until then), validates it at `:now` and walks the cached publication points the same way (a level's points in parallel, results folded in order; inside `Validate.point/5` files are decoded and children validated in parallel too, #169), adding signed objects (`point(..., objects: true)`: the first entry is the point's manifest, valid when the point is accepted, with the point's problems; then entries `kind: :object` with `type`, valid when the EE certificate validates and `Lumina.CMS.check/1` passes, #131, and for a ROA `Lumina.ROA.check/2` too, #171); the result's `objects` list holds CA certificates and signed objects, `vrps` the VRPs of the valid ROAs (#164: `ROA.vrps/1` entries plus `ta`, the `:name` option, which the CLI sets to `Validate.ta_name/1` of the TAL path, D-032, and `uri`, the ROA's; one per ROA, duplicates kept for `--wide`, D-033; sorted IPv4 first, then address, prefix length, maxLength, AS, trust anchor, URI; a ROA from a last valid copy counts), `unlisted` counts files not on a manifest; `summary/2` (counts per type) and `failed?/2` drive the CLI. Publication points (#133): `Lumina.PublicationPoint.process(ca, path, key, now, opts)` decides from the cache copy whether a valid CA's point is usable (RFC 9286 §6, RFC 9981 §4): the manifest the CA's SIA names, in the caRepository, valid (EE via `Chain.child/6`, `CMS.check/1`, `Manifest.check/1`), its signedObject URI its own, current, listing the CA's CRL, every listed file present with the right SHA-256. Returns `%{status: :accepted | :failed, manifest, problems, files}` (`files`: listed name => path, only when accepted); `rules/0` lists the point-only rules; `crl/6` gives a child certificate's CRL result from the CRLs the manifest lists only (RFC 9829 §3.2, #116: `crl_not_on_manifest` otherwise), and `Validate` uses it; `read_crl/3` reads a CRL file from the point. `unlisted` names files not on the manifest. The walk and `validate` use it through `Validate.point/5`, which returns `%{point:, entries:}` (#134). Progress (#96, D-036): `Lumina.Progress` events go through a `:progress` function option (TA, walk, sync emit them, and `Validate.run/3` for `lumina validate` and `lumina vrps`, #180; `Progress.emit/2` is free without one) and the CLI draws them on stderr by default, a status line on a terminal, timestamped lines elsewhere, none with `--quiet` (`--progress` is accepted and is the default). CLI tests that check stderr add `--quiet` through `Lumina.Test.Quiet.args/1`; `ProgressTest` covers the default. The escript sends Logger output to stderr, so stdout is only the summary. `lumina sync` checks `Rsync.check/1` first (rsync >= 3.1.0, the first on PATH or `--rsync PATH`; macOS's `/usr/bin/rsync` is openrsync, too old) and exits 0, 1 (a trust anchor wasn't retrieved or its own publication point wasn't fetched, `Sync.ta_synced?/1`; the cache is locked; or rsync is missing or too old; a fetch failing further down only warns, D-037, #187) or 2 (usage); tests drive it with `CLI.run/4` and its test-only `internal` options (`:remap`, `:tal_dir`, ...).

Lumina has no runtime dependencies. Third-party packages are for development only (`only: [:dev, :test], runtime: false`), pinned to exact versions in `mix.exs`.

Mix's default `.gitignore` ignores `/doc/`. This repo removes that line because `doc/` holds the RFC library. Keep it that way, and send any generated ExDoc output somewhere else.

## Source of truth

- The implementation is derived **only** from the RFC text documents, kept in `doc/rfc/`. Don't rely on other RPKI implementations' behavior or code; cite the RFC and section when making a validation decision.
- ASN.1 modules are extracted verbatim from the RFC texts into `asn1/rfc/`. Compiler workarounds live in `asn1/patches/` (strict unified diffs; each hunk has a `-- LUMINA PATCH (<kind>): <reason>` comment, and its kind limits what it may change), and `asn1/build/` holds the result. Never edit `rfc/` or `build/`, and never apply RFC errata by patching; enforce them in validation. See `asn1/README.md`. `mix compile` turns `asn1/build/` into Erlang in `gen/asn1/` (git-ignored), using the `lumina_asn1` compiler defined in `mix.exs`. Decode and encode only through `Lumina.ASN1` (`decode(:pkix, :Certificate, der)`), which never raises and rejects trailing bytes. Values are maps keyed by ASN.1 field names. `Lumina.ASN1` accepts BER, so check every object from a repository with `Lumina.DER.check/1` (schema-less walk) and, for typed values, `Lumina.DER.check_canonical/3` (decode + re-encode must give identical bytes). DER errors carry the rule, the X.690 clause (02/2021 numbering) and a byte offset. RFC 3779 resources: `Lumina.Resources.decode_ip/1` and `decode_as/1` turn extension values into integer prefixes and ranges. Canonical-form problems are reported by `ip_issues/1` and `as_issues/1`, never enforced during decoding. Certificates: `Lumina.Certificate.decode/1` gives a struct with every field, decoded extensions (`extension_value/2`, `sia_uris/2`, `aia_uris/2`), and the exact signed bytes (`tbs_der`, `issuer_der`, `subject_der`, `public_key.der`). Profile violations decode; only non-DER or unparseable input fails, with the failing layer in the error. `Lumina.CRL.decode/1` does the same for CRLs (`number/1`, `revoked?/2`, exact `tbs_der`/`issuer_der`). Extensions of certificates, CRLs and CRL entries are `Lumina.Extension` structs (`value` is decoded, `:unknown` or `{:malformed, reason}`). Signed objects: `Lumina.SignedObject.decode/1` decodes the CMS envelope (EE certificate with its exact DER, signers with decoded signed attributes and `signed_attrs_der`, the exact SET OF bytes the signature covers). eContent stays raw, and `decode_econtent/1` decodes it through the content-type table, which replaces the patched-out `CONTENT-TYPE` objects. RFC 7935 §2: SignerInfo uses `rsaEncryption`, and RPs accept that or `sha256WithRSAEncryption`. ROAs: `Lumina.ROA.decode/1` (full object) or `decode_econtent/1` (bare payload; an AFI other than IPv4/IPv6 fails as `invalid_address_family`, §4.3.1, F-012); `vrps/1` gives AS, prefix and effective maxLength; `issues/1` reports RFC 9582 §4.3 encoding problems; `check(roa, ee)` validates the content (§4, §5, #171): `roa_version`, `roa_ee_no_ip_resources`, `roa_ee_ip_inherit`, `roa_ee_as_resources`, `roa_prefix_outside_ee` (prefixes outside the EE certificate's addresses, named) and the MUSTs of `issues/1` are errors that make the whole ROA invalid; its SHOULDs (`superfluous_max_length`, `not_canonical_order`, `duplicate_address`) only warn (D-030). ROA fixtures are `m7-roa-*`; Barry can't put an AS extension on a ROA's EE certificate, and under an inheriting CA it gives the ROA's EE certificate `inherit`, which §5 forbids. Manifests: `Lumina.Manifest.decode/1` (full object) or `decode_econtent/1`; `names/1`, `hash/2`; `check/1` reports content problems (RFC 9286 §4.2.1, §4.2.2, §4.4: version 0, thisUpdate before nextUpdate, both `YYYYMMDDHHMMSSZ` with no fractional seconds (RFC 5280 §4.1.2.5.2, F-019, #48), number within 20 octets, SHA-256, file names and IANA-registered extensions, F-032, no duplicates, at least one file: `manifest_empty`, RFC 9286 §7 and erratum 7118, #37), and `lumina validate` adds them to the manifest's entry. An empty file list still decodes (the module is kept as published, F-001). Any repository file: `Lumina.Object.decode(file_name, bytes)` / `decode_file(path)` picks the decoder by registered extension (`.cer .crl .mft .roa .gbr .sig .tak`), checks a signed object's eContent type against it, and returns errors whose layer `Lumina.Object.layer/1` names (`:der`, `:asn1`, `:envelope`, `:econtent`, `:type`, `:file`). CMS envelope: `Lumina.CMS.check/1` = `profile/1` + `verify/1`. `verify/1` checks the message-digest attribute (SHA-256 of the eContent, RFC 5652 §5.4) and the signature over `signed_attrs_der` with the EE key (`Lumina.Crypto.verify_cms/4`, which accepts rsaEncryption or sha256WithRSAEncryption). `profile/1` checks a decoded `SignedObject` against RFC 6488 §2.1/§3 item 1 as updated by RFC 9589 (signing-time required, binary-signing-time rejected), with RFC 7935 §2 algorithms; absent rsaEncryption parameters only warn (RFC 3370 §3.2 wants NULL; Barry omits them, F-031); problems in the `Lumina.Profile` shape. `SignedObject.crls` is `nil` when absent, `[]` when present and empty. Signatures: `Lumina.Crypto.verify/2` checks a `Certificate` or `CRL` with its issuer's `public_key` (a TA with its own), `verify/4` any signed bytes; only sha256WithRSAEncryption over 2048-bit RSA keys with exponent 65,537 (RFC 7935), verified as RFC 8017 §8.2.2 says (encode the expected EMSA-PKCS1-v1_5 block and compare bytes, never parse the signature). Errors are `%{rule, rfc, message}`. Either key OID is read (F-027). Profile: `Lumina.Profile.certificate(cert, kind, at)` (kind `:ta`, `:ca` or `:ee`) runs `basic_fields(cert, at)` (RFC 6487 §4.1-4.7, validity at `at` per §7.2) and `extensions(cert, kind)` (§4.8 with RFC 7318; unknown critical extensions reject, unknown non-critical ones warn, D-013), returning `%{rule, rfc, field, message, severity}` problems; `passes?/1` is true when none is an `:error` (a sha256WithRSAEncryption key algorithm only warns, D-018). `Profile.crl(crl, issuer_cert, at)` checks a CRL (RFC 6487 §5, RFC 9829 §3.1: v2, exactly AKI and CRL Number, AKI = SHA-1 of the issuer's key, CRL Number non-critical and 0..2^159-1, no entry extensions, the signature); a CRL past its nextUpdate only warns `:stale_crl` (D-016). Chain validation (`Lumina.Chain`, RFC 6487 §7.2 points 1-7): `ta(cert, tal, at)`, `crl(crl_or_nil, issuer, at)` (once per CA) and `child(cert, kind, issuer, crl_result, at, opts)` (issuer name, AKI = SHA-1 of the issuer's key, signature, profile, revocation, resource inclusion; a missing or invalid CRL makes the child invalid), each `%{valid, problems}`; `crl_uri/1` gives the CRLDP's rsync URI, and finding that CRL is the caller's job (D-015). Effective resources (#153, D-026): `Lumina.Resources.effective(cert, issuer_effective)` gives `%{ipv4, ipv6, as}` with `inherit` resolved from the issuer's (RFC 3779 §2.2.3.5, §3.2.3.3); inheriting a kind the issuer doesn't hold is holding none, not an error (manifest EE certificates must inherit every kind, RFC 9286 §5.1, F-033); `Chain.ta/3` and `Chain.child/6` (option `resources:`, the issuer's effective set; without it, the issuer's own) return `resources`, and the walk, `Validate.point/5` and `PublicationPoint.process/5` (option `resources:`) carry each CA's down. Resource sets (#152, D-027): `Resources.intervals(list, kind)` gives one kind as sorted, merged integer intervals; `encompasses?(x, y)` (RFC 6487 §7.1) compares IPv4, IPv6 and AS numbers separately and as sets, not range by range (F-034); `outside(y, x)` is what `y` holds beyond `x`, as prefixes where they fit, else ranges, for `format/2`; `held(x)` merges `x` once for comparing many children of one issuer (`Chain.child/6` option `held:`, #169). Resource inclusion (RFC 6487 §7.2 point 6, #154, D-028): `Chain.child/6` rejects a CA or EE certificate whose effective resources its issuer's don't encompass, `resources_not_encompassed` with the resources outside in the message (`"10.0.0.0/8, AS64500 not held by the issuer"`); the certificate is invalid as a whole (no RFC 8360), so the walk doesn't follow an overclaiming CA. Reporting (#155): `Chain.rule_text/1` shows a problem's rule with the resources outside (`resources_not_encompassed: 2.0.0.0/16`) and `Chain.overclaim?/1` spots one; `lumina validate` (CA and EE certificates) and `lumina sync` (CA certificates only; the walk validates no signed objects) list overclaims that way and print `overclaims: N` per TAL when there are any; they count as invalid toward D-022. A manifest EE certificate that lists a kind (IPv4, IPv6, AS numbers) explicitly instead of inheriting it gets one warning, `manifest_ee_resources_not_inherit` (RFC 9286 §5.1, #157, D-029, F-035), naming the kinds; an absent kind doesn't warn. Barry writes explicit resources on every manifest a fixture doesn't declare in its tree, so most fixture manifests carry it; a declared manifest can be given `inherit` (`m6-mft-ee-inherit`). Overclaim fixtures are `m6-overclaim-*`; Barry copies an overridden resource set to the node's children and writes only prefixes in certificates, never address ranges. AS lists in a `case.repo` must be in increasing order (RFC 3779 §3.2.3.4). Revocation fixtures use Barry's `obj.tbsCertList.revokedCertificates = [ serial ]` (D-021). CRL fixtures override `[node: ca1.crl]`, so they list `ca1.crl` in the tree. Barry writes hexadecimal INTEGERs as raw octets (`0x80...` is negative); use decimal for large positive values. Barry gives TAs serial 0, so every fixture's `case.repo` sets the TA's to 1 (F-029); keep that in new fixtures.
- Test cases are developed together with Barry (an RPKI test-case tool; URL still to be filled in `GOAL.md`).

## Design decisions

Maintainer decisions about how Lumina works are recorded in `doc/decisions.md` (D-001, D-002, ...), with the reason and where they were discussed. Record new ones there when the maintainer makes them, and follow them. Example: D-001 sets the CLI model, `lumina <command> [flags] [arguments]`, so new functionality is added as a command with its own flags, never as a top-level `--flag`.

## RFC findings log

Record every RFC erratum, ambiguity, missing or obsolete reference, and tooling incompatibility you run into in `doc/rfc-findings.md`, as you find it. It's talk material for the maintainer.
- Before relying on an RFC's ASN.1 module, worked example or test vector, check its errata at <https://www.rfc-editor.org/errata.json> and record anything relevant.
- Each entry quotes the text, gives the official errata status (ID, or "none found" with the date) and links the issue that resolves it.
- Never submit errata to the RFC Editor yourself. Mark new ones "not reported" and tell the maintainer.
- Our own mistakes don't belong in the entries. If they say something about the process, add them to "Process notes".

## Workflow rules

- Work is tracked on GitHub: milestones for large work packages, atomic and testable issues filed against milestones.
- One PR per issue.
- Unit-test everything that can be unit tested. Each issue defines the tests it must pass.
- Every long-running operation reports progress, on by default (D-036): a status line on stderr on a terminal, timestamped lines elsewhere, nothing only with `--quiet`, through `Lumina.Progress` events (a `:progress` option); stdout stays the command's output. A new long-running command or stage isn't done without it, and its tests.
- An issue can't be closed unless its tests pass, unless the maintainer (Carlos) explicitly acknowledges otherwise. A milestone can't be closed unless all tests pass.
